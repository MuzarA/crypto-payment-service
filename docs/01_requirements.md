# Требования: Crypto Payment Service

## 1. Назначение

Crypto Payment Service — бэкенд-сервис (минимальная платёжная система), который принимает от других сервисов запросы на оплату и списывает деньги в криптовалюте (BTC) с кошелька клиента через open-source криптокошелёк **Bitcoin Core**.

Сервис без пользовательского интерфейса. С ним работают другие программы по HTTP (REST API, JSON). Для ручной проверки есть автоматическая документация Swagger UI (`/docs`).

## 2. Участники (акторы)

| Актор | Кто это | Что делает |
|---|---|---|
| **Сервис-клиент (Merchant)** | Внешняя система, например интернет-магазин | Создаёт платёж, узнаёт его статус, запрашивает возврат |
| **Клиент (Customer)** | Покупатель магазина | Владеет криптокошельком, с которого списываются деньги. С нашим сервисом напрямую не общается |
| **Криптокошелёк (Bitcoin Core)** | Внешняя open-source система | Хранит кошельки клиентов и кошелёк сервиса, проводит переводы |

## 3. Глоссарий

- **Платёж (Payment)** — один запрос на списание определённой суммы с конкретного клиента по конкретному заказу.
- **Кошелёк клиента** — кошелёк в Bitcoin Core, имя которого совпадает с `customer_id`.
- **Кошелёк сервиса** — кошелёк `_payment_service`, куда поступают списанные деньги.
- **txid** — идентификатор транзакции в блокчейне, доказательство перевода.
- **regtest** — локальная тестовая сеть Bitcoin: монеты бесплатные, блоки создаются командой.

## 4. Функциональные требования

### Оплата

| ID | Требование |
|---|---|
| **FR-1** | Сервис принимает запрос на оплату `POST /api/v1/payments` с полями `order_id`, `customer_id`, `amount`, `currency`. |
| **FR-2** | Сервис проверяет, есть ли у клиента кошелёк. Если кошелька нет, платёж получает статус `FAILED` с причиной `WALLET_NOT_FOUND`. |
| **FR-3** | Если кошелёк есть, сервис запрашивает данные клиента (имя кошелька, адрес для возврата, число транзакций). Статус становится `WALLET_VERIFIED`. |
| **FR-4** | Отдельным запросом сервис проверяет баланс. Если баланс меньше, чем `amount + резерв на комиссию сети`, статус `FAILED` с причиной `INSUFFICIENT_FUNDS`. Иначе статус `FUNDS_CONFIRMED`. |
| **FR-5** | Сервис переводит `amount` с кошелька клиента на кошелёк сервиса и сохраняет `txid`. Статус `COMPLETED`, сообщение «Деньги сняты успешно». |
| **FR-6** | Если кошелёк недоступен или вернул ошибку, статус `FAILED` с причиной `WALLET_ERROR`. |
| **FR-7** | Ответ на запрос оплаты всегда содержит итоговый статус, `txid` (при успехе) или причину отказа. |
| **FR-8** | Сервис только **принимает** деньги. Выплаты третьим лицам не поддерживаются. |

### Возврат (refund)

| ID | Требование |
|---|---|
| **FR-9** | Магазин может запросить возврат `POST /api/v1/payments/{id}/refund`. |
| **FR-10** | Вернуть можно только платёж в статусе `COMPLETED`. Для других статусов сервис отвечает `409 INVALID_STATUS`. Повторный возврат невозможен. |
| **FR-11** | Деньги возвращаются на адрес клиента, полученный на шаге FR-3. Комиссия сети за возврат вычитается из суммы возврата. |
| **FR-12** | После возврата статус `REFUNDED` и сохраняется `refund_txid`. Если кошелёк недоступен, статус остаётся `COMPLETED` и возврат можно повторить. |
| **FR-13** | Частичный возврат в этой версии не поддерживается: возвращается вся сумма. |

### Просмотр

| ID | Требование |
|---|---|
| **FR-14** | `GET /api/v1/payments/{id}` возвращает платёж с полной историей смены статусов. |
| **FR-15** | `GET /api/v1/payments` возвращает последние платежи магазина (по умолчанию 50, максимум 200). |
| **FR-16** | `GET /health` показывает, что сервис работает. |

### Правила и проверки

| ID | Требование |
|---|---|
| **BR-1** | Сумма больше 0, не более 8 знаков после запятой (1 сатоши = 0.00000001 BTC). |
| **BR-2** | Поддерживается только валюта `BTC`. |
| **BR-3** | `customer_id`: от 1 до 64 символов (латиница, цифры, `_`, `-`), не может начинаться с `_`. Так нельзя обратиться к служебным кошелькам. |
| **BR-4** | Пара (`merchant_id`, `order_id`) уникальна. Повторный запрос с тем же `order_id` возвращает `409 DUPLICATE_ORDER` и id существующего платежа. Это защита от двойного списания. |
| **BR-5** | Магазин видит и возвращает только свои платежи. Чужой платёж для него «не найден» (404). |
| **BR-6** | Переходы между статусами строго ограничены машиной состояний (см. state-диаграмму). |

## 5. Нефункциональные требования

| ID | Требование |
|---|---|
| **NFR-1 Безопасность** | Каждый запрос магазина содержит заголовок `X-API-Key`. Без него или с неверным ключом ответ `401`. Порт RPC кошелька не открыт в интернет: к нему обращается только сервис внутри Docker-сети. |
| **NFR-2 Точность денег** | Суммы хранятся и передаются как `Decimal` или строка, без `float`, чтобы не терять точность. |
| **NFR-3 Надёжность** | Платежи хранятся в SQLite на постоянном томе Docker и сохраняются после перезапуска. Каждый шаг платежа сохраняется сразу. |
| **NFR-4 Развёртывание** | Сервис запускается одной командой `docker compose up -d --build` на любом облачном Linux-сервере (DigitalOcean и т.п.). |
| **NFR-5 Расширяемость** | Новый кошелёк (например, Ethereum) или другую базу данных можно подключить новым классом-адаптером, не меняя бизнес-логику. |
| **NFR-6 Тестируемость** | Бизнес-логика покрыта автотестами, которым не нужен настоящий узел Bitcoin. |
| **NFR-7 Наблюдаемость** | Каждый шаг платежа пишется в лог. У каждого платежа есть история статусов с временем. |
| **NFR-8 Производительность** | Обработка одного платежа в regtest занимает не больше нескольких секунд. |

## 6. API (кратко)

| Метод | Путь | Ответ |
|---|---|---|
| POST | `/api/v1/payments` | `201` + платёж (`COMPLETED` или `FAILED`), `409`, `401`, `422` |
| GET | `/api/v1/payments/{id}` | `200`, `404` |
| GET | `/api/v1/payments?limit=50` | `200` |
| POST | `/api/v1/payments/{id}/refund` | `200` (`REFUNDED`), `404`, `409`, `502` |
| GET | `/health` | `200` |

Пример запроса:

```json
POST /api/v1/payments
X-API-Key: demo-key

{ "order_id": "order-1001", "customer_id": "alice", "amount": "0.01", "currency": "BTC" }
```

Пример ответа:

```json
{
  "id": "6f1c…",
  "status": "COMPLETED",
  "message": "Деньги сняты успешно",
  "txid": "a3b9…",
  "amount": "0.01",
  "history": [
    {"status": "CREATED"}, {"status": "WALLET_VERIFIED"},
    {"status": "FUNDS_CONFIRMED"}, {"status": "COMPLETED"}
  ]
}
```

Почему ответ `201`, даже если оплата не прошла? Запись о платеже создана в любом случае, а результат оплаты передаётся в поле `status`. Так магазин всегда получает `id` и может посмотреть причину отказа.

## 7. Ограничения и допущения (учебная имитация)

- Сервис имеет доступ к кошелькам клиентов в Bitcoin Core и сам подписывает перевод. В настоящей платёжной системе клиент подтверждает платёж сам, например переводом на выставленный адрес. По заданию это допустимое упрощение.
- Используется сеть **regtest**, настоящие деньги не задействованы. `AUTO_MINE=true` создаёт блок после каждого перевода, чтобы транзакция сразу подтвердилась.
- Курсы валют и конвертация (USD → BTC) вне рамок проекта.
- Возврат только полный (см. FR-13).
