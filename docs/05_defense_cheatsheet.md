# Шпаргалка к защите (мидтерм, ~3 минуты)

## Рассказ о проекте за 30 секунд

> «Это бэкенд-сервис для приёма оплаты в биткоинах. Другой сервис, например магазин, отправляет запрос: заказ, клиент, сумма. Мой сервис проверяет, есть ли у клиента кошелёк в Bitcoin Core, получает данные клиента, отдельным запросом проверяет баланс, списывает деньги на кошелёк сервиса и возвращает статус с txid. Возврат тоже поддерживается. Архитектура гексагональная: бизнес-логика зависит только от интерфейсов, а Bitcoin Core и SQLite подключены как адаптеры. Сервис запущен в Docker на DigitalOcean, кошелёк работает в тестовой сети regtest».

## Что показать (по порядку)

1. `http://<IP>:8000/docs`: сервис работает на облачном сервере.
2. `./scripts/demo.sh`: запросы и ответы (успех, отказы, возврат).
3. Диаграммы: `docs/02_diagrams.md`.
4. Код: `app/services/payment_service.py`, метод `_process`. По шагам в нём видна вся логика.

## Вероятные вопросы и ответы

**Какой кошелёк используете и почему?**
Bitcoin Core, эталонный open-source кошелёк. У него есть JSON-RPC API и несколько кошельков на одном узле. Сеть regtest: монеты бесплатные, блоки создаются по команде.

**Как сервис узнаёт, есть ли кошелёк у клиента?**
Вызывает RPC `listwallets`, а если кошелька там нет, ещё и `listwalletdir`. Если кошелёк есть на диске, но не загружен, вызывает `loadwallet`. Код: `BitcoinCoreWallet._load_if_exists`.

**Как списываются деньги?**
`getnewaddress` берёт адрес кошелька сервиса, затем `sendtoaddress` от кошелька клиента на этот адрес. Bitcoin Core возвращает txid.

**Что если денег не хватает?**
Проверка происходит дважды. Сначала `getbalance`: баланс должен покрывать сумму плюс резерв на комиссию. Затем, если узел всё равно ответит ошибкой `-6 Insufficient funds`, она превращается в `InsufficientFundsError`. В обоих случаях статус `FAILED / INSUFFICIENT_FUNDS`, деньги не тронуты.

**Как работает возврат? Почему нельзя вернуть дважды?**
Деньги отправляются из кошелька сервиса на адрес клиента, сохранённый при оплате. Вернуть можно только из статуса `COMPLETED`. После возврата статус `REFUNDED` — конечный, поэтому машина состояний не пустит повторный возврат (409).

**Что если магазин отправит один и тот же запрос дважды?**
Пара `merchant_id + order_id` уникальна (и в коде, и в БД через `UNIQUE`). Второй запрос получит `409 DUPLICATE_ORDER` и id первого платежа. Двойного списания не будет.

**Как защищён сервис?**
У каждого магазина свой API-ключ в заголовке `X-API-Key`. Магазин видит только свои платежи. RPC-порт Bitcoin Core не открыт наружу. Пароль RPC хранится в `.env`.

**Почему суммы в Decimal?**
Float неточен (`0.1+0.2≠0.3`). В биткоине точность 8 знаков (сатоши).

**Где здесь SOLID?** (подробно: `docs/03_architecture_solid.md`)
- **S**: `PaymentStateMachine` только проверяет переходы, `BitcoinRpcClient` только отправляет RPC.
- **O**: новый кошелёк = новый класс, реализующий `WalletGateway`, без изменений `PaymentService`.
- **L**: `FakeWallet` вместо `BitcoinCoreWallet`, на этом построены тесты.
- **I**: интерфейс кошелька разделён на `WalletReader` и `WalletTransfer`.
- **D**: `PaymentService` получает интерфейсы через конструктор, а собирается всё в `main.py`.

**Какая архитектура?**
Hexagonal (Ports & Adapters) со слоями `api → services → domain`. Порты лежат в `app/ports`, адаптеры в `app/adapters`.

**Что такое regtest и `AUTO_MINE`?**
regtest — локальная сеть биткоина. Транзакция подтверждается только в блоке, поэтому при `AUTO_MINE=true` сервис создаёт блок после каждого перевода. Только для тестовой сети.

**Чем отличается от настоящей платёжной системы?**
В реальности клиент сам подписывает перевод, а сервис выставляет адрес и ждёт подтверждений (обычно несколько блоков). Здесь сервис имеет доступ к кошельку клиента, как разрешено в задании («имитация»). Ещё не хватает вебхуков для уведомления магазина и конвертации валют.

**Как бы вы масштабировали?**
SQLite заменить на PostgreSQL (новый адаптер `PaymentRepository`), запустить несколько копий API за балансировщиком, перевести списание в очередь (async) и отправлять результат вебхуком.

**Почему ответ 201 даже при FAILED?**
Платёж (запись) создан в любом случае. Результат оплаты — это бизнес-статус в поле `status`, а не ошибка протокола. По `id` магазин всегда может посмотреть причину.

## Файлы, которые стоит знать наизусть

| Файл | Что в нём |
|---|---|
| `app/services/payment_service.py` | весь сценарий оплаты и возврата |
| `app/domain/state_machine.py` | правила переходов (state-диаграмма в коде) |
| `app/ports/wallet.py` | интерфейсы кошелька |
| `app/adapters/bitcoin_core_wallet.py` | работа с Bitcoin Core |
| `app/main.py` | сборка (Dependency Injection), ошибки → HTTP |
